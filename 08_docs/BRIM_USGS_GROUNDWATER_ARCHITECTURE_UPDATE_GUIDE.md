# BRIM USGS Groundwater Architecture and Update Guide

## Purpose

This guide documents the current BRIM USGS groundwater architecture after the RF027–RF038 groundwater live-feed and history work. It is intended to make the groundwater system updateable over time without accidentally overwriting useful static/historical data.

## Layer roles

BRIM should maintain two related but distinct USGS groundwater products.

### 1. Static USGS Wells layer

The static layer is the statewide reference backbone. It may include active, inactive, historical, sparse, and long-record wells. It is useful for broad site discovery, historical context, and general USGS groundwater-site awareness.

Recommended behavior:

- Keep the static layer broad.
- Cluster heavily for performance.
- Keep popup/hover concise and stable.
- Use scalar most-recent-water-level fields where available.
- Do not embed large plot JSON or live-feed history graphics in the static layer unless a later performance test supports it.
- Update appender-first: never drop existing static wells unless a QA review explicitly approves that change.

### 2. Ops Live Groundwater layer

The Ops Live groundwater layer is the active/recent analytical layer. It is designed for recent water-level screening, project review support, and quick spatial reconnaissance.

Current behavior:

- Candidate wells are generated by `02_preprocess/30_export_usgs_groundwater_live_inputs.R`.
- The candidate export uses the existing static BRIM groundwater backbone plus a modern USGS Water Data API discovery query for recent California groundwater field measurements, parameter `72019`.
- Daily latest values are generated by `brim-live-data-feeds/scripts/build_usgs_groundwater_latest_ca.R` and published as static GeoJSON by GitHub Pages.
- Historical context is generated locally by `02_preprocess/31_build_usgs_groundwater_history_summary.r` and joined into the daily GeoJSON when the history summary CSV is present.
- Ops Live browser popups/hover include latest depth-to-water, history percentiles, water-year mean mini plots, and grouped/co-located marker behavior for nested wells.

## Update cadence

### Daily automatic update

The GitHub Action `Build USGS CA groundwater latest GeoJSON` should run daily.

It should only:

1. Read the committed candidate CSV.
2. Fetch latest field-measurement groundwater levels for those candidates.
3. Join the committed history summary if available.
4. Publish `docs/data/usgs_groundwater_latest_ca.geojson` and its summary JSON.

It should not:

- Discover brand-new wells.
- Download full history.
- Rebuild static RDS/cache products.
- Touch the main BRIM map HTML.

### Monthly, quarterly, or project-driven live-candidate refresh

Run from the PortaTreasure2 root:

```r
source("02_preprocess/30_export_usgs_groundwater_live_inputs.R")
source("02_preprocess/31_build_usgs_groundwater_history_summary.r")

local({
  old_wd <- getwd()
  on.exit(setwd(old_wd), add = TRUE)
  setwd("brim-live-data-feeds")
  source("scripts/build_usgs_groundwater_latest_ca.R")
})
```

Then commit these live-feed repo files:

```text
brim-live-data-feeds/data/input/usgs_groundwater_latest_index_ca.csv
brim-live-data-feeds/data/input/usgs_groundwater_history_summary_ca.csv
brim-live-data-feeds/scripts/build_usgs_groundwater_latest_ca.R
brim-live-data-feeds/.github/workflows/build-usgs-groundwater-latest-ca.yml
```

Then rerun the GitHub Action.

### Occasional static groundwater refresh

Static groundwater should be updated less often and with more QA.

Recommended process:

1. Run `02_preprocess/32_audit_usgs_groundwater_static_live_architecture.r`.
2. Review:
   - `04_processed_data/qa/usgs_groundwater_live_only_append_preview.csv`
   - `04_processed_data/qa/usgs_groundwater_static_live_overlap_preview.csv`
   - `04_processed_data/qa/usgs_groundwater_static_nested_coord_groups.csv`
   - `04_processed_data/qa/usgs_dataretrieval_modernization_inventory.csv`
3. Create an appender patch that writes a preview RDS first, not the production static RDS.
4. Promote to the static layer only after QA.
5. Rebuild core cache and then final map.

## Nested/co-located wells

Nested wells occur where multiple USGS groundwater records share the same mapped coordinate. They may represent separate completions, separate PVC wells in one boring, or closely related site records.

Ops Live currently handles this in the browser:

- Single-coordinate/single-record wells draw as individual markers.
- Multiple records at the same coordinate draw as one grouped marker.
- The grouped popup lists the individual wells in a scrollable record list.

For the static layer, do not assume standard clustering fully solves nested wells. Marker clustering can spiderfy some overlapping markers, but exact-coordinate circle markers can still be confusing depending on zoom, cluster settings, and layer implementation. The preferred static approach should be chosen after the RF038 audit quantifies static nested-coordinate groups.

Candidate static options:

1. Leave static clustering as-is and add a popup/hover note where duplicate-coordinate groups exist.
2. Add a precomputed nested-group count field to the static map-ready layer.
3. Use a grouped/nested marker strategy similar to Ops Live for the static layer, but only after performance testing with the full 44k+ static layer.

## dataRetrieval modernization

BRIM should progressively eliminate legacy NWIS calls from USGS scripts.

Avoid in new code:

- `whatNWISdata()`
- `readNWISsite()`
- `readNWISuv()`
- `readNWISdv()`

Prefer modern Water Data API helpers where appropriate:

- `read_waterdata_field_measurements()` for groundwater field measurements such as parameter `72019`.
- `read_waterdata_monitoring_location()` for monitoring-location metadata.
- `read_waterdata_latest_continuous()` for latest continuous streamflow/stage values.
- `read_waterdata_continuous()` for continuous time-series history when needed.
- `read_waterdata_daily()` for daily values when needed.
- `read_waterdata_ts_meta()` for time-series metadata.

Modernization should be incremental. Do not blindly replace every call in one patch. For each script:

1. Identify the exact legacy call and its expected columns.
2. Replace with the closest modern Water Data API call.
3. Normalize field names back to the existing BRIM schema.
4. Write QA comparing row counts, site counts, date ranges, and key fields.
5. Keep old outputs until the new output is verified.

## Current important scripts

### Static/legacy backbone

`02_preprocess/05_usgs_streamgages_wells.r`

- Builds broad static streamgage and groundwater well products.
- Still contains legacy NWIS-style calls and should be modernized carefully.
- Should not be rerun destructively until a modernization/appender workflow is ready.

### Cached latest groundwater lookup for static/backbone workflows

`02_preprocess/15_usgs_gw_latest_water_levels.r`

- Fetches latest field-measurement groundwater levels for wells in `USGS_GW_final.rds`.
- Uses modern `read_waterdata_field_measurements()`.
- Writes a separate lookup table and does not directly edit the main static well RDS.

### Live candidate export

`02_preprocess/30_export_usgs_groundwater_live_inputs.R`

- Builds the committed candidate CSV used by the daily GitHub latest feed.
- Supplements the old static/cache backbone with modern API discovery for recent CA `72019` sites.
- This is the main pathway for newly active/recent USGS groundwater wells to enter Ops Live.

### Historical enrichment

`02_preprocess/31_build_usgs_groundwater_history_summary.r`

- Builds local cached history and water-year summaries.
- Incrementally backfills newly added candidate wells.
- Creates the compact history summary CSV that the daily feed can join into the hosted GeoJSON.

### Architecture audit

`02_preprocess/32_audit_usgs_groundwater_static_live_architecture.r`

- Non-destructive QA script.
- Compares static and live groundwater products.
- Quantifies live-only additions, nested/co-located wells, and remaining legacy dataRetrieval calls.
